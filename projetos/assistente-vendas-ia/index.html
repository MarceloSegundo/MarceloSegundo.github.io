Estudo de caso · 01

Assistente de vendas com IA para uma corretora de planos de saúde

Um chat no estilo WhatsApp em que a IA conduz a venda: qualifica o cliente, monta a composição familiar e apresenta a cotação, com preço e cobertura vindos do banco de dados, nunca inventados pelo modelo.

Papel
Projeto solo: backend, frontend, infra e deploy
Período
2026 · cerca de 2 meses de desenvolvimento · 153 commits
Stack
Java 21, Quarkus, LangChain4j, PostgreSQL (Flyway), imagem nativa GraalVM/Mandrel, React 19 + Vite + TypeScript, JWT RSA
Versão anterior
Spring Boot 3 + Spring AI + Spring Security
Infra
Frontend na Vercel, API e banco no Railway, CI no GitHub Actions
Status
Em produção. Link sob pedido (projeto para cliente, apresentado de forma anônima).

Contexto e problema

A corretora queria um consultor virtual na landing page: alguém que conversasse com o cliente, coletasse os dados necessários (nome, data de nascimento, CPF ou CNPJ, telefone e quem entra no plano), recomendasse o plano adequado à idade e à região e entregasse ao corretor humano, pelo WhatsApp, um lead já qualificado e com a cotação pronta.

O risco óbvio de pôr um LLM para vender plano de saúde é ele inventar preço, carência ou cobertura. O projeto inteiro gira em torno de impedir isso sem perder o tom de conversa.

Arquitetura

A cada mensagem, a API carrega o lead e o estágio atual do funil, monta o contexto com o que já foi coletado e chama o modelo oferecendo só as ferramentas permitidas naquele estágio. Quando o modelo decide, por exemplo, chamar getPlanPrice, o LangChain4j executa o método Java, que consulta o PostgreSQL, e devolve o resultado ao modelo. O frontend recebe texto e "cards" estruturados (plano, encaminhamento) e os renderiza como componentes, não como texto livre.

Decisões e trade-offs

Preço e cobertura só via tool calling

Decisão
O prompt proíbe o modelo de calcular preço; o valor exibido é sempre o retorno de uma ferramenta que consulta a tabela de preços por plano, acomodação e faixa etária. O card de cotação é montado pelo backend a partir desses dados.
Por quê
Em venda de plano de saúde, um preço ou uma cobertura inventada é um problema sério para a corretora. Os dados comerciais ficam num lugar só, editável no painel administrativo.
Custo
A correção passa a depender de o modelo realmente chamar a ferramenta. Ele às vezes não chama, o que levou às duas decisões seguintes.

Funil de estágios no banco, com ferramentas liberadas por estágio

Decisão
Cada conversa tem um estágio persistido (nome → nascimento → CPF/CNPJ → telefone → composição familiar → cotação → encaminhamento). O bot não escolhe o próprio objetivo: o backend lê o estágio, injeta a instrução do turno e expõe só as ferramentas daquele passo. Cada ferramenta de salvamento já avança o estágio antes de retornar.
Por quê
Transforma uma conversa aberta numa máquina de estados verificável: em cada turno o modelo só consegue salvar o dado que aquele estágio espera, e o progresso da venda fica registrado no banco, não na memória do modelo.
Custo
Menos flexibilidade na conversa, e um estágio novo exige mexer no enum do funil, no registro de ferramentas, no contexto do turno e no serviço do lead.

Rede de segurança para quando o modelo "esquece" a ferramenta

Decisão
Depois de cada resposta, uma heurística verifica se a mensagem do usuário parecia conter o dado esperado (uma data, um nome, um CPF) e se o estágio de fato avançou. Se não avançou, a API dispara um turno de correção. Se mesmo assim o card de cotação ou de encaminhamento não vier, o backend o gera a partir do banco.
Por quê
O modelo às vezes confirma o dado em texto ("ótimo, anotei sua data") sem chamar a ferramenta, e o dado nunca é salvo. A heurística é feita com regex, sem biblioteca de NER, porque as opções em português não se dão bem com imagem nativa.
Custo
Um turno extra de LLM quando a correção dispara, e uma heurística que precisa de manutenção quando surge um padrão novo de resposta.

Migração de Spring Boot para Quarkus com imagem nativa

Decisão
A primeira versão foi em Spring Boot 3 com Spring AI e Spring Security com JWT próprio. Ela foi portada para Quarkus com LangChain4j, Hibernate Panache e SmallRye JWT com chaves RSA, e hoje roda como imagem nativa compilada com Mandrel.
Como
Os dois módulos ficaram lado a lado no repositório com a mesma estrutura de pacotes (chat, plan, lead, config, security), o que permitiu comparar o comportamento camada por camada durante a migração.
Custo
O build nativo cobrou caro, e cada problema ficou documentado:
  • bindings JNI do Netty/OpenSSL que precisaram ser inicializados em runtime, sem arrastar junto classes puramente Java do mesmo pacote;
  • um filtro de CORS que lia configuração na fase de inicialização estática e derrubava o container no boot, resolvido lendo a configuração sob demanda;
  • DTOs que o Jackson não conseguia serializar no binário nativo porque os endpoints declaravam o tipo genérico Response, resolvido declarando o tipo concreto.
Pôr a versão Quarkus no ar também revelou sete problemas independentes de deploy, vários mascarados um pelo outro.

Deploy dividido e modelo com fallback

Decisão
Frontend estático na Vercel, API e banco no Railway, migrações com Flyway. O GitHub Actions roda os testes do backend e o lint e o build do frontend nos pushes para a branch de desenvolvimento e nos pull requests para a principal. O acesso ao LLM passa pelo OpenRouter, com um modelo principal e troca automática para um modelo de fallback se a API falhar.
Por quê
Separar front e API permite publicar cada um no ritmo dele. O fallback evita que uma instabilidade de um provedor derrube a venda no meio da conversa.
Custo
CORS e URLs por ambiente para manter em dois provedores. Os dois modelos precisam se comportar de forma parecida com o mesmo prompt e as mesmas ferramentas.

Telas do painel

Painel administrativo protegido por JWT, de onde a corretora mantém planos, faixas etárias, preços e promoções, a mesma base que o bot consulta. Capturas da demo local com dados fictícios.

O código é privado e o cliente não é identificado. Faço demonstração em entrevista, incluindo a comparação entre as versões Spring Boot e Quarkus.
